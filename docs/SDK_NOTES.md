## Stripe Python (`stripe`) — 16.0.0 · spike 0.7 PASS (11/11, twice in a row)
Docs: https://docs.stripe.com/payments/place-a-hold-on-a-payment-method · https://docs.stripe.com/api/payment_intents/capture?lang=python  ·  Checked: 2026-10-17 by B
Spike: `spikes/07-stripe-manual-capture/spike.py` (run with `uv run`, Python 3.12, test-mode key only)
- **Client style:** `StripeClient(key)` and `client.v1.payment_intents.create({...}, options={"idempotency_key": ...})`. Request params are a dict passed positionally. `capture(id)` and `cancel(id, {...})` follow the same pattern.
- **`payment_method_types` is rejected** on new accounts ("no longer supported"). Use `allowed_payment_method_types: ["card"]` to stay card-only. Server-side confirm uses `payment_method: "pm_card_visa"` with `confirm: True`.
- **Statuses:** after create and confirm → `requires_capture` with `amount_capturable` = amount. `capture` → `succeeded`. `cancel` → `canceled`, `amount_received` 0.
- **Authorization window:** read it from `charge.payment_method_details.card.capture_before`. The test Visa showed about 7 days. Docs: Visa customer-initiated 7 days, merchant-initiated about 4 days 18 hours. Uncaptured intents auto-cancel after 7 days. **So `hold.release_at` must come well before `capture_before`.**
- **Idempotency:** use the Mulligan `action_id` as the key (`mulligan-<action_id>`) and in `metadata.mulligan_action_id`. A retry with identical params returns the same PaymentIntent. A retry with the same key and **different params** raises `stripe.IdempotencyError`. The gateway should treat that as a bug, not retry it.
- **Wrong-state calls** raise `stripe.InvalidRequestError` with code `payment_intent_unexpected_state` (capture after cancel, cancel after capture). Rewind after capture can't cancel, so it has to refund instead: the action becomes `compensable`. This matches the plan.

## Photon 2.0 API (`@photon-ai/api`) — 0.5.0 · spike 0.6 PASS (approve 1.5 s, reject 2.2 s; budget 5 s)
Docs: https://photon.codes/docs/beta/get-started/imessage · https://photon.codes/docs/beta/api-client/credentials  ·  Checked: 2026-10-17 by B
Spike: `spikes/06-photon-imessage/` (`npm run spike`, parser tests: `npx tsx --test parse.test.ts`). Node 24+ required.
- **Use `@photon-ai/api`, not `spectrum-ts`.** Our dashboard is the Photon 2.0 beta (app.beta.photon.codes). `spectrum-ts` 12.x is the older "Stable" product and rejects `pho_prj_` project IDs (`422 VALIDATION_ERROR`). In 2.0, the project API key (`pho_sk_…`) goes in `Authorization: Bearer`, and only works under `/v1/projects/{projectId}`. Base URL is `https://api.photon.codes`.
- **Calls:** `new Photon({ headers: { Authorization: \`Bearer ${key}\` } })`, then `photon.projects.listMessages({ path: { id }, query })` and `photon.projects.sendMessage({ path: { id }, headers: { "idempotency-key": … }, body: { spaceId, senderId, content: { type: "text", format: "plain", text } } })`. Message items are typed loosely, so we cast them to a local type (`sentBy.handle`, `receivedBy.id`, `space.{id,kind}`, `content.{type,text}`, `createdAt`).
- **`listMessages` `direction` is `received` | `sent`.** `dispatched` is a message *status*, not a direction. Send returns status `dispatched` (accepted, not proof of delivery).
- **Shared lines can't text first** (`403 SHARED_LINE_INBOUND_REQUIRED`). The approver must text the line once, after their assignment. Then we send into that `space.id` with `senderId` = the inbound message's `receivedBy.id`. **Contract impact:** Mulligan has to keep each approver's `spaceId`/`senderId`, and the demo setup includes "approver texts the line once".
- **No threaded replies on shared lines:** `parentMessageId` gets `409 SPACE_NOT_SENDABLE` ("Replies are not supported for this Space"). Send confirmations as plain messages.
- **The approver must be on iMessage.** An Android phone receives our outbound text (as RCS), but its RCS reply never reaches the API. We tested with the Mac's Messages app signed in with an Apple ID email, added in the dashboard via "Use an iMessage email instead". That gives the email its own shared line. Handles can be an E.164 phone or an email, so we compare phones by digits and emails case-insensitively.
- **Polling** every 1 s with `createdSince` = send time and `order: asc` got no 429s. The docs' sample polls every 2 s and suggests live events (WebSocket) for long-running agents. That's worth a look in Phase 2. Shared lines also have plan seat limits per assigned handle.
- Lag is measured as local poll time minus the server's `createdAt`, so clock skew of a second or so is possible. That's fine for a 5 s budget.

## Sentry Python (`sentry-sdk`) MCPIntegration — 2.72.0 with `mcp` 2.3.0 · spike 0.8 PASS (8/8, twice in a row)
Docs: https://docs.sentry.io/platforms/python/integrations/mcp/ · https://docs.sentry.io/platforms/python/tracing/instrumentation/custom-instrumentation/mcp-module/  ·  Checked: 2026-10-17 by B
Spike: `spikes/08-sentry-mcp/spike.py` (`uv run`, Python 3.12). FastAPI + `MCPServer` on 127.0.0.1:8001/mcp, Streamable HTTP, project `mulligan-gateway`.
- **Integration:** `from sentry_sdk.integrations.mcp import MCPIntegration`, then `sentry_sdk.init(..., traces_sample_rate=1.0, integrations=[MCPIntegration()])`. sentry-sdk 2.72 patches mcp v2's lowlevel server, which covers `MCPServer`. The docs mark MCP support as beta. Logs need sentry-sdk ≥ 2.68.0.
- **Produces:** one transaction per MCP request, with an `op: mcp.server` span named `tools/call <tool>` carrying `mcp.tool.name`, `mcp.method.name`, `mcp.request.id`, `mcp.transport` (`http`). Resource and prompt calls get `resources/read …` and `prompts/get …`.
- **mcp 2.x renamed `FastMCP` → `MCPServer`** (`from mcp.server import MCPServer`). Mount it with `app.mount("/", mcp.streamable_http_app(streamable_http_path="/mcp"))` and run `mcp.session_manager.run()` in the FastAPI lifespan. Client: `Client(streamable_http_client(url, http_client=httpx2.AsyncClient(headers=…)))`. Note it's **`httpx2`**, not httpx.
- **⚠ Tool arguments always go to Sentry.** `mcp.request.argument.*` is attached regardless of `send_default_pii`, which only gates results and prompts (`include_prompts`). The gateway **must** scrub these in `before_send_transaction`, since agent arguments can contain customer data. The spike does this and asserts it.
- **⚠ No MCP session ID.** mcp 2.x clients speak protocol **`2026-07-28`**, which is sessionless (`server/discover`, no `initialize`, no `mcp-session-id` header). So `mcp.session.id` is absent. **Contract impact (Stream A):** a Mulligan `session_id` can't come from the MCP session. Derive it ourselves, e.g. per agent token plus an explicit `X-Mulligan-Session` header or a `mulligan_status`/`start_session` call, with an idle timeout as fallback. Older clients (Claude Code, Devin) may still use the handshake-era protocol with sessions. Spikes 0.1 and 0.2 should record which protocol each one sends.
- To link a timeline row to Sentry, store the span's `trace_id` as `sentry_trace_id` on the Action. Verified in Sentry UI by B (Explore → Traces, filter `mcp.method.name is tools/call`): 4 `tools/call pg_query` spans, one per run. Sentry also indexes them as `gen_ai.tool.name`, so they appear in its AI/agent views. The transaction shows as `<unlabeled transaction>`, so the gateway should name it (e.g. `sentry_sdk.get_current_scope().set_transaction_name(f"mcp tools/call {tool}")`) to keep the trace list readable.

## MCP Python SDK + FastAPI + uvicorn + cloudflared (spikes 0.1, 0.2) — mcp 2.3.0 · FastAPI 0.143.3 · uvicorn 0.54.0 · cloudflared 2026.10.0
Docs: https://py.sdk.modelcontextprotocol.io/run/asgi/ · https://py.sdk.modelcontextprotocol.io/run/authorization/ · https://py.sdk.modelcontextprotocol.io/run/deploy/ · https://py.sdk.modelcontextprotocol.io/protocol-versions/ · https://code.claude.com/docs/en/mcp · https://docs.devin.ai/work-with-devin/mcp  ·  Checked: 2026-10-17 by A
- **0.1 pass.** Claude Code 2.1.301 lists and calls the tool through `claude mcp add --scope local --transport http mulligan <url> --header "Authorization: Bearer <token>"` and through `claude -p --mcp-config`. The server sees the token (`get_access_token()`) and the `Mcp-Session-Id`, with the handshake forced as below.
- **0.2 pass pending Devin.** Through a quick tunnel to `127.0.0.1:8001`, the Python client and Claude Code list and call the tool. A missing or wrong token gets 401. `/healthz`, `/api/*`, `/docs`, `/openapi.json` and `/.well-known/*` get 404 on the tunnel origin, because the tunnel only reaches the MCP port and it serves `/mcp` only. Devin's Test tools and a Devin session call are still to do (`spikes/01-mcp-http/README.md`).
- **v2 renames.** `from mcp.server import MCPServer` (was `FastMCP`), `from mcp.server.mcpserver import Context`. Serving options (`transport_security`, `stateless_http`, `streamable_http_path`) moved from the constructor to `streamable_http_app()`. The SDK uses `httpx2`, not `httpx`. Client: `from mcp import Client`; pass headers on your own `httpx2.AsyncClient` to `streamable_http_client(url, http_client=...)` (it rejects `headers=`).
- **Protocol 2026-07-28 has no sessions and no `Mcp-Session-Id`.** Against an SDK v2 server, Claude Code 2.1.301 negotiates 2026-07-28 by default, so the server saw no session id. Decision: wrap the MCP app in a small ASGI check (`ForceHandshake` in `spikes/01-mcp-http/server.py`). An authenticated request whose `MCP-Protocol-Version` isn't a handshake version gets a 400 JSON-RPC error. Clients in `auto` mode (Python SDK, Claude Code) treat that as a legacy server, run `initialize` (2025-11-25) and get a session id. Unauthenticated requests pass through, so they still get 401. A client pinned to 2026-07-28 can't connect. For Claude Code only, `MCP_PROTOCOL_NEGOTIATION=legacy` or `MCP_SDK_GENERATION=v1` gets the same result from the client side.
- **Inside a tool:** declare `ctx: Context`. Session id: `ctx.headers.get("mcp-session-id")`. Protocol: `ctx.protocol_version`. Agent: `get_access_token().client_id` (from `mcp.server.auth.middleware.auth_context`). The SDK binds a session to the token that opened it.
- **Auth:** `MCPServer(token_verifier=..., auth=AuthSettings(issuer_url=..., resource_server_url=None))`. The two arguments must be passed together. `issuer_url` is required but unused when `resource_server_url=None`. That setting also keeps `/.well-known/oauth-protected-resource` off and leaves `resource_metadata` out of the 401, so clients don't start an OAuth flow. A missing or wrong token gets `401` with `WWW-Authenticate: Bearer error="invalid_token"`, before any MCP parsing.
- **Mounting in FastAPI:** use `app.mount("/", mcp.streamable_http_app(...))` and keep the default path, so the endpoint is `/mcp`. The host app's lifespan must enter `mcp.session_manager.run()`: a mounted app's lifespan never runs, and the first request fails with "Task group is not initialized". `/mcp/` 307-redirects to `/mcp`, so configure clients with `/mcp` exactly.
- **FastAPI routes outside auth:** an app-level `dependencies=[Depends(auth)]` doesn't cover FastAPI's own `/docs`, `/redoc` and `/openapi.json` (200 without a token), and it doesn't cover mounted apps either. Turn those routes off on both apps (`docs_url=None, redoc_url=None, openapi_url=None`); MCP auth comes from the SDK.
- **Two servers, one process:** `await asyncio.gather(uvicorn.Server(api_cfg).serve(), uvicorn.Server(mcp_cfg).serve())`. Module-level state is shared: the REST route reads calls the MCP tool recorded. Each `serve()` installs its own SIGINT/SIGTERM handlers, so the second replaces the first, but uvicorn re-raises the captured signal on exit, so Ctrl+C and SIGTERM still stop both cleanly.
- **Allowed hosts (DNS-rebinding check):** by default only `127.0.0.1:<port>`, `localhost:<port>` and `[::1]:<port>` are allowed. cloudflared forwards the public `Host`, so through the tunnel a request with no token gets 401 (auth runs first) and one with a token gets 421 "Invalid Host header". Fix: `TransportSecuritySettings(allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*", host, f"{host}:*"])`. Entries are exact strings (no `*.trycloudflare.com`), so the quick-tunnel host is passed in at start (`MULLIGAN_MCP_PUBLIC_HOST`), and a new tunnel URL means a server restart.
- **Bind and proxy headers:** bind both ports to `127.0.0.1` and point the tunnel at `http://127.0.0.1:8001`. `--url http://localhost:8001` also works against a 127.0.0.1-only bind (cloudflared falls back from `::1`). uvicorn trusts `X-Forwarded-*` from 127.0.0.1 by default and cloudflared connects from there, so the app sees `https` and the caller's IP, and redirects stay `https`.
- **cloudflared on venue Wi-Fi:** QUIC (UDP 7844) took about 60 s of dial timeouts before registering; `--protocol http2` registered in about 15 s. Creating a quick tunnel can also time out (`failed to request quick Tunnel`), so retry. The URL changes on every restart.
- **Tool results:** a bare `-> dict` return comes back as text content with `structured_content=None`. Return a TypedDict or Pydantic model to get structured output.
