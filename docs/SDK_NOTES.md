## Stripe Python (`stripe`) — 16.0.0 · spike 0.7 PASS (11/11, twice in a row)
Docs: https://docs.stripe.com/payments/place-a-hold-on-a-payment-method · https://docs.stripe.com/api/payment_intents/capture?lang=python  ·  Checked: 2026-10-17 by B
Spike: `spikes/07-stripe-manual-capture/spike.py` (run with `uv run`, Python 3.12, test-mode key only)
- **Client style:** `StripeClient(key)` and `client.v1.payment_intents.create({...}, options={"idempotency_key": ...})`. Request params are a dict passed positionally. `capture(id)` and `cancel(id, {...})` follow the same pattern.
- **`payment_method_types` is rejected** on new accounts ("no longer supported"). Use `allowed_payment_method_types: ["card"]` to stay card-only. Server-side confirm uses `payment_method: "pm_card_visa"` with `confirm: True`.
- **Statuses:** after create and confirm → `requires_capture` with `amount_capturable` = amount. `capture` → `succeeded`. `cancel` → `canceled`, `amount_received` 0.
- **Authorization window:** read it from `charge.payment_method_details.card.capture_before`. The test Visa showed about 7 days. Docs: Visa customer-initiated 7 days, merchant-initiated about 4 days 18 hours. Uncaptured intents auto-cancel after 7 days. **So `hold.release_at` must come well before `capture_before`.**
- **Idempotency:** use the Mulligan `action_id` as the key (`mulligan-<action_id>`) and in `metadata.mulligan_action_id`. A retry with identical params returns the same PaymentIntent. A retry with the same key and **different params** raises `stripe.IdempotencyError`. The gateway should treat that as a bug, not retry it.
- **Wrong-state calls** raise `stripe.InvalidRequestError` with code `payment_intent_unexpected_state` (capture after cancel, cancel after capture). Rewind after capture can't cancel, so it has to refund instead: the action becomes `compensable`. This matches the plan.

## Photon 2.0 API (`@photon-ai/api`) — 0.5.0 · spike 0.6 PASS (approve 1.5 s, reject 2.2 s; budget 5 s)
Docs: https://photon.codes/docs/beta/get-started/imessage · https://photon.codes/docs/beta/api-client/credentials  ·  Checked: 2026-10-17 by B
Spike: `spikes/06-photon-imessage/` (`npm run spike`, parser tests: `npx tsx --test parse.test.ts`). Node 24+ required.
- **Use `@photon-ai/api`, not `spectrum-ts`.** Our dashboard is the Photon 2.0 beta (app.beta.photon.codes). `spectrum-ts` 12.x is the older "Stable" product and rejects `pho_prj_` project IDs (`422 VALIDATION_ERROR`). In 2.0, the project API key (`pho_sk_…`) goes in `Authorization: Bearer`, and only works under `/v1/projects/{projectId}`. Base URL is `https://api.photon.codes`.
- **Calls:** `new Photon({ headers: { Authorization: \`Bearer ${key}\` } })`, then `photon.projects.listMessages({ path: { id }, query })` and `photon.projects.sendMessage({ path: { id }, headers: { "idempotency-key": … }, body: { spaceId, senderId, content: { type: "text", format: "plain", text } } })`. Message items are typed loosely, so we cast them to a local type (`sentBy.handle`, `receivedBy.id`, `space.{id,kind}`, `content.{type,text}`, `createdAt`).
- **`listMessages` `direction` is `received` | `sent`.** `dispatched` is a message *status*, not a direction. Send returns status `dispatched` (accepted, not proof of delivery).
- **Shared lines can't text first** (`403 SHARED_LINE_INBOUND_REQUIRED`). The approver must text the line once, after their assignment. Then we send into that `space.id` with `senderId` = the inbound message's `receivedBy.id`. **Contract impact:** Mulligan has to keep each approver's `spaceId`/`senderId`, and the demo setup includes "approver texts the line once".
- **No threaded replies on shared lines:** `parentMessageId` gets `409 SPACE_NOT_SENDABLE` ("Replies are not supported for this Space"). Send confirmations as plain messages.
- **The approver must be on iMessage.** An Android phone receives our outbound text (as RCS), but its RCS reply never reaches the API. We tested with the Mac's Messages app signed in with an Apple ID email, added in the dashboard via "Use an iMessage email instead". That gives the email its own shared line. Handles can be an E.164 phone or an email, so we compare phones by digits and emails case-insensitively.
- **Polling** every 1 s with `createdSince` = send time and `order: asc` got no 429s. The docs' sample polls every 2 s and suggests live events (WebSocket) for long-running agents. That's worth a look in Phase 2. Shared lines also have plan seat limits per assigned handle.
- Lag is measured as local poll time minus the server's `createdAt`, so clock skew of a second or so is possible. That's fine for a 5 s budget.

## MCP Python SDK + FastAPI + uvicorn + cloudflared (spikes 0.1, 0.2) — mcp 2.3.0 · FastAPI 0.143.3 · uvicorn 0.54.0 · cloudflared 2026.10.0
Docs: https://py.sdk.modelcontextprotocol.io/run/asgi/ · https://py.sdk.modelcontextprotocol.io/run/authorization/ · https://py.sdk.modelcontextprotocol.io/run/deploy/ · https://py.sdk.modelcontextprotocol.io/protocol-versions/ · https://code.claude.com/docs/en/mcp · https://docs.devin.ai/work-with-devin/mcp  ·  Checked: 2026-10-17 by A
- **0.1 pass.** Claude Code 2.1.301 lists and calls the tool through `claude mcp add --scope local --transport http mulligan <url> --header "Authorization: Bearer <token>"` and through `claude -p --mcp-config`. The server sees the token (`get_access_token()`) and the `Mcp-Session-Id`, with the handshake forced as below.
- **0.2 pass pending Devin.** Through a quick tunnel to `127.0.0.1:8001`, the Python client and Claude Code list and call the tool. A missing or wrong token gets 401. `/healthz`, `/api/*`, `/docs`, `/openapi.json` and `/.well-known/*` get 404 on the tunnel origin, because the tunnel only reaches the MCP port and it serves `/mcp` only. Devin's Test tools and a Devin session call are still to do (`spikes/01-mcp-http/README.md`).
- **v2 renames.** `from mcp.server import MCPServer` (was `FastMCP`), `from mcp.server.mcpserver import Context`. Serving options (`transport_security`, `stateless_http`, `streamable_http_path`) moved from the constructor to `streamable_http_app()`. The SDK uses `httpx2`, not `httpx`. Client: `from mcp import Client`; pass headers on your own `httpx2.AsyncClient` to `streamable_http_client(url, http_client=...)` (it rejects `headers=`).
- **Protocol 2026-07-28 has no sessions and no `Mcp-Session-Id`.** Against an SDK v2 server, Claude Code 2.1.301 negotiates 2026-07-28 by default, so the server saw no session id. Decision: wrap the MCP app in a small ASGI check (`ForceHandshake` in `spikes/01-mcp-http/server.py`). An authenticated request whose `MCP-Protocol-Version` isn't a handshake version gets a 400 JSON-RPC error. Clients in `auto` mode (Python SDK, Claude Code) treat that as a legacy server, run `initialize` (2025-11-25) and get a session id. Unauthenticated requests pass through, so they still get 401. A client pinned to 2026-07-28 can't connect. For Claude Code only, `MCP_PROTOCOL_NEGOTIATION=legacy` or `MCP_SDK_GENERATION=v1` gets the same result from the client side.
- **Inside a tool:** declare `ctx: Context`. Session id: `ctx.headers.get("mcp-session-id")`. Protocol: `ctx.protocol_version`. Agent: `get_access_token().client_id` (from `mcp.server.auth.middleware.auth_context`). The SDK binds a session to the token that opened it.
- **Auth:** `MCPServer(token_verifier=..., auth=AuthSettings(issuer_url=..., resource_server_url=None))`. The two arguments must be passed together. `issuer_url` is required but unused when `resource_server_url=None`. That setting also keeps `/.well-known/oauth-protected-resource` off and leaves `resource_metadata` out of the 401, so clients don't start an OAuth flow. A missing or wrong token gets `401` with `WWW-Authenticate: Bearer error="invalid_token"`, before any MCP parsing.
- **Mounting in FastAPI:** use `app.mount("/", mcp.streamable_http_app(...))` and keep the default path, so the endpoint is `/mcp`. The host app's lifespan must enter `mcp.session_manager.run()`: a mounted app's lifespan never runs, and the first request fails with "Task group is not initialized". `/mcp/` 307-redirects to `/mcp`, so configure clients with `/mcp` exactly.
- **FastAPI routes outside auth:** an app-level `dependencies=[Depends(auth)]` doesn't cover FastAPI's own `/docs`, `/redoc` and `/openapi.json` (200 without a token), and it doesn't cover mounted apps either. Turn those routes off on both apps (`docs_url=None, redoc_url=None, openapi_url=None`); MCP auth comes from the SDK.
- **Two servers, one process:** `await asyncio.gather(uvicorn.Server(api_cfg).serve(), uvicorn.Server(mcp_cfg).serve())`. Module-level state is shared: the REST route reads calls the MCP tool recorded. Each `serve()` installs its own SIGINT/SIGTERM handlers, so the second replaces the first, but uvicorn re-raises the captured signal on exit, so Ctrl+C and SIGTERM still stop both cleanly.
- **Allowed hosts (DNS-rebinding check):** by default only `127.0.0.1:<port>`, `localhost:<port>` and `[::1]:<port>` are allowed. cloudflared forwards the public `Host`, so through the tunnel a request with no token gets 401 (auth runs first) and one with a token gets 421 "Invalid Host header". Fix: `TransportSecuritySettings(allowed_hosts=["127.0.0.1:*", "localhost:*", "[::1]:*", host, f"{host}:*"])`. Entries are exact strings (no `*.trycloudflare.com`), so the quick-tunnel host is passed in at start (`MULLIGAN_MCP_PUBLIC_HOST`), and a new tunnel URL means a server restart.
- **Bind and proxy headers:** bind both ports to `127.0.0.1` and point the tunnel at `http://127.0.0.1:8001`. `--url http://localhost:8001` also works against a 127.0.0.1-only bind (cloudflared falls back from `::1`). uvicorn trusts `X-Forwarded-*` from 127.0.0.1 by default and cloudflared connects from there, so the app sees `https` and the caller's IP, and redirects stay `https`.
- **cloudflared on venue Wi-Fi:** QUIC (UDP 7844) took about 60 s of dial timeouts before registering; `--protocol http2` registered in about 15 s. Creating a quick tunnel can also time out (`failed to request quick Tunnel`), so retry. The URL changes on every restart.
- **Tool results:** a bare `-> dict` return comes back as text content with `structured_content=None`. Return a TypedDict or Pydantic model to get structured output.
## PostgreSQL + psycopg (spike 0.3, typed-tool undo) — PostgreSQL 16.15 on `timescale/timescaledb:latest-pg16` (TimescaleDB 2.30.2, digest `sha256:6f139d56…`), `psycopg[binary]==3.3.6`, Python 3.12
Docs: https://www.postgresql.org/docs/16/sql-altertable.html · https://www.postgresql.org/docs/16/sql-insert.html · https://www.postgresql.org/docs/16/functions-json.html · https://www.postgresql.org/docs/16/functions-admin.html · https://www.postgresql.org/docs/16/sql-declare.html · https://www.psycopg.org/psycopg3/docs/advanced/cursors.html#server-side-cursors · https://www.psycopg.org/psycopg3/docs/basic/from_pg2.html#multiple-statements-in-the-same-query · https://www.psycopg.org/psycopg3/docs/basic/adapt.html  ·  Checked: 2026-10-17 by A
- Code is in `spikes/03-pg-typed-undo/`. `run_spike.py` runs 44 checks, and all pass on two runs in a row. `mulligan_prod_setup.sql` holds the audit table, the trigger, the roles and `mulligan_trash` for `infra/db/prod-db/`.
- **PASS: checksum after undo equals checksum before.** This holds for each of 9 actions, undone newest first, and for the whole session. It includes a customer delete that cascaded into `orders`, `order_items` (a grandchild), `support_tickets` and `customer_notes` (`ON DELETE SET NULL`).
- **PASS: a dropped table comes back whole.** It returns with the same OID and its data, PK, unique and plain indexes, identity sequence (same last value), trigger, grants, and the inbound FK from `price_overrides`, which is still enforced. The catalog snapshot after undo equals the one taken before the drop.
- **PASS: `mulligan_ro` can't see the trash.** It has no USAGE on `mulligan_trash` or `mulligan_audit`. Selecting a trashed table fails with `permission denied for schema mulligan_trash`.
- **PASS: a runaway `pg_query` is killed.** `SELECT pg_sleep(10)` is cancelled by `statement_timeout` after 5.00 s. A 1 s per-call timeout, below the role's 5 s backstop, fires at 1.01 s.
- **Decision: sort by FK dependency, never `DEFERRABLE` FKs.** One action is undone in one transaction, in three passes. First, delete the rows it inserted, children first. Second, re-insert the rows it deleted, parents first, with tables topo-sorted from `pg_constraint` (`contype = 'f'`, both ends among the action's tables). Third, put back the columns it changed, parents first, newest audit row first. Replaying in plain reverse audit order fails with an FK violation for the 3-level cascade, the self-referencing cascade and a `p → c → gc` probe.
- **Self-referencing FK** (`employees.manager_id ON DELETE CASCADE`): a table-level sort can't order rows within one table. So that table's rows are topo-sorted by their own FK values: a row waits for the row whose key its FK points at. Deleting the root of a 7-person tree re-inserted ids 10, 3, 12, 7, 15, 1, 2. A row cycle (A manages B, B manages A) or a cycle between tables raises `UndoError`. It would need a two-phase insert (FK column NULL, then UPDATE), which only works on nullable columns.
- **A cascade is logged parent first.** FK actions queue their row events behind the outer statement's, so the parent's audit row comes first and its children follow level by level, whatever the audit trigger is named. `pg_trigger_depth()` is 1 for cascaded rows too, so it can't mark them. The write tools use `RETURNING mulligan_audit.canon_row(tgt)` to tag the rows the statement touched directly. Every other audit row in the action came from a cascade.
- **Re-inserting into `GENERATED ALWAYS AS IDENTITY`.** A plain insert fails with `cannot insert a non-DEFAULT value into column "id"` (428C9). This works, and Postgres also accepts it on tables with no identity column: `INSERT INTO t (<non-generated cols>) OVERRIDING SYSTEM VALUE SELECT r.<cols> FROM mulligan_audit.audit_log a CROSS JOIN LATERAL jsonb_populate_record(NULL::t, a.old_row) r WHERE a.id = $1`. Leave `GENERATED ALWAYS AS (...) STORED` columns out of the list. Identity sequences aren't rewound, so ids have gaps after undo. Checksums cover rows only.
- **Setting the action id.** `SET LOCAL` can't take a bind parameter, so use `SELECT set_config('mulligan.action_id', $1, true)`, which does the same thing. After that transaction ends, `current_setting('mulligan.action_id', true)` returns `''`, not NULL, in the same session. The trigger skips logging on both.
- **63-byte identifiers.** Postgres silently truncates longer names at a character boundary and only raises a NOTICE. `<table>__<action_id>` for a 58-byte table name became `…_channel_v2__act`, losing the id. Trash names are `<action_id, lowercased>__<table>`, cut to 63 bytes on a UTF-8 boundary, so the unique part always survives. The original name is kept in the inverse payload.
- **`ALTER TABLE ... SET SCHEMA`** moves the table's indexes, constraints and owned (identity or serial) sequences with it. Triggers, grants, the OID and inbound FKs (which point by OID) are unchanged. Index and sequence names are unique per schema, so moving a second table with the same name failed with `relation "dup_pkey" already exists in schema "mulligan_trash"`. The soft drop therefore renames every index and owned sequence to `<action_id>_i<n>` / `_s<n>` first, and undo renames them back. Renaming a PK or unique index renames its constraint too. Undo is a conflict if any original name is already taken in the target schema.
- **What the trash still exposes.** A view over the dropped table keeps working, and `mulligan_ro` read 12 trashed rows through `legacy_pricing_v`. Trashed table names (not their data) show up in `pg_class` and `information_schema.tables` for `mulligan_ro`, because its SELECT grant moves with the table. Child tables can still insert rows that reference the trashed table.
- **`pg_query` uses a psycopg named (server-side) cursor.** psycopg sends `DECLARE ... CURSOR FOR <sql>` over the extended protocol, which has four effects. A multi-statement string fails with `cannot insert multiple commands into a prepared statement`. Anything other than a SELECT is a syntax error. A data-modifying CTE is refused. One `FETCH` of `row_cap + 1` rows enforces the cap. A plain cursor with no parameters uses the simple protocol and would run several statements. Calling `set_config('statement_timeout', '0', true)` inside the query doesn't stop the timer that is already running. With no parameters, `%` and `{}` in the agent's SQL pass through untouched.
- **How values are canonicalized and hashed.** Values go through `mulligan_audit.canon_row()`, which is `to_jsonb(row)` inside a function pinned to `TimeZone=UTC`, `DateStyle=ISO`, `IntervalStyle=iso_8601`, `extra_float_digits=1`, `bytea_output=hex` and `lc_monetary=C`. `field_hash()` is the sha256 hex of the field's jsonb text.
  - NULL: a NULL column hashes `null`. An absent row or field (deleted row, dropped table) hashes the empty string.
  - Numbers: numerics keep their stored scale, so `numeric(12,4)` 1.5 is `1.5000` and unconstrained numerics keep the input's scale. Floats use the shortest form that round-trips (`0.30000000000000004`), with `"NaN"` and `"Infinity"` as strings.
  - Times: timestamptz renders as `"2026-03-08T09:59:59.123456+00:00"`, timestamp has no offset, and interval renders as `"P1Y2M3DT4H5M6.789S"`.
  - jsonb uses jsonb's own normalized text: keys in order, duplicate keys dropped.
  - `extra_float_digits=0` makes `to_jsonb` emit `0.3`, which is why it's pinned. Writes made under `America/St_Johns` with `extra_float_digits=0`, and undone under `Asia/Kathmandu` with `extra_float_digits=3`, still match.
- **40 of 42 column types round-trip exactly** through `canon_row` → `jsonb_populate_record`: integers, numeric, float4/float8 (including NaN, ±Infinity and 5e-324), text with tabs, quotes, backslashes and astral characters, `char(n)` padding, date and timestamp (including infinity), time/timetz, interval, bytea, uuid, inet/cidr/macaddr, enum, ranges, 1-D and 2-D arrays, jsonb, xml, money, varbit, tsvector, point, composite and domain types. Two are lossy. `json` columns come back normalized (key order, whitespace, duplicate keys). A JSON `null` in a jsonb column comes back as SQL NULL. Use jsonb in the demo schema.
- **Hashes are computed in SQL, never in Python,** because jsonb's text spacing differs from `json.dumps`. psycopg's default jsonb loader turns every number into a float, so undo never sends values through Python. Each undo statement reads its audit row by id and converts it back with `jsonb_populate_record`.
- **psycopg needs ISO DateStyle.** Its C timestamptz loader fails on non-ISO output (`NotImplementedError: can't parse timestamptz with DateStyle 'SQL, DMY'`), so keep DateStyle ISO on gateway connections.
- **`after_hashes` keys.** Columns are `postgres:<table>/<pk>/<column>`. The table is a bare name in `public` and `schema.table` elsewhere. A composite PK is joined with `,`, and `%`, `/` and `,` are percent-escaped in every segment. INSERT hashes every column and UPDATE hashes the changed columns. DELETE adds a row key `postgres:<table>/<pk>` and a drop adds `postgres:<table>`, both with the absent hash. Generated columns are skipped. Hashes recomputed from the live DB just before each undo matched for all 9 actions.
- **Write guards.**
  - The table must have a PK.
  - A write is refused if the table, or any table an FK action can reach from it (CASCADE, SET NULL or SET DEFAULT, followed recursively), has no enabled audit trigger.
  - An empty filter needs `all: true`.
  - Table and column names are checked against the catalog.
  - Values go in as one jsonb parameter.
- **Roles.** `mulligan_gw` must own the app tables, because the soft drop needs ownership, and it needs CREATE on `public` and `mulligan_trash`. `enable_schema()` gives `mulligan_ro` SELECT on tables, but views need their own grant. The setup file must run as a superuser.
- **Not covered.** TRUNCATE (the tools never issue it), customer BEFORE triggers that rewrite restored values (for example `updated_at = now()`), hypertables, partitioned tables, and undoing an `ON UPDATE CASCADE`.
## Notion API `2026-03-11` + notion-client (Python) `3.1.0`
Docs: https://developers.notion.com/reference/versioning · https://developers.notion.com/docs/upgrade-guide-2026-03-11 · https://github.com/ramnes/notion-sdk-py · Checked: 2026-10-17 by A
Spike 0.4 (Notion restore): **PASS** on both criteria. `spikes/04-notion-restore/spike.py run` restores the page to the original normalized hash, and with a teammate edit it keeps and flags that one block and matches the original everywhere else.
- **Versions.** `2026-03-11` is the current API version. notion-client 3.1.0 (Python, community-maintained; Notion's only official SDK is JS `@notionhq/client` 5.27.1) still defaults to `2025-09-03`, so pass `Client(notion_version="2026-03-11")`. 3.1.0 already lets `position` and `in_trash` through its body filters.
- **Trash field.** `2026-03-11` renamed `archived` to `in_trash` in requests and responses for pages, blocks, databases and data sources. Pages also return a separate `is_archived` field, which isn't the trash flag. `blocks.delete` sets `in_trash: true`, and `blocks.update(id, in_trash=False)` brings the block back with the same id and children.
- **Workspace-level pages can be trashed but never untrashed by the API** ("Unarchiving workspace level pages not supported by the API"). Every page Mulligan must be able to rewind sits under a parent page shared with the integration. The demo pricing doc lives under "Acme Widgets", and seed/reset must keep it there. Hold or block `notion_trash_page` on any workspace-level page.
- While a page is trashed, `GET /blocks/{page}/children` returns 404 `object_not_found`, the page drops out of search, and block edits inside it fail with `validation_error`. So a teammate can't fix a trashed doc. Snapshot before trashing, and untrash first on rewind (newest-first order does this anyway). Read any child order only after that untrash.
- **Ordering.** Untrash always re-adds the block at the **end** of its parent, not where it was, and there's no move-block endpoint. To put blocks back with their original ids, trash every block from the first out-of-place one onward, then untrash them in the right order: 2 requests per block in that tail. The cheaper alternative is to recreate the block with `position: {type: "after_block", after_block: {id}}` (or `{type: "start"}`), but that gives it a new id. Use the previous sibling recorded at delete time as the anchor. Rewinding newest first guarantees that sibling is already back in place.
- `2026-03-11` replaced the flat `after` param on append with `position` (`after_block` / `start` / `end`). With `position`, the append response's `results` holds the new block **followed by every later sibling**, so take `results[0]` and don't assume `len == 1`.
- **Ids.** The API returns dashed UUIDs (e.g. in `block.parent.page_id`). Normalize every id to the dashed form before comparing. `NOTION_PRICING_PAGE_ID` in `.env` is the page URL: take the last 32-hex run.
- **Normalizing for hashes.** Drop `plain_text`, `href`, nulls, ids and timestamps, and keep `annotations`. Compare against what the API echoes back, not what you sent: responses fill in the default annotations.
- **Conflicts.** Hash each block without its children, plus `in_trash`, and each property as `{type, value}`. Record the hash from the write's response. At rewind, a block or property whose current hash differs was changed by a human: keep it and flag it.
- **Recreating blocks.** `table`, `column_list`, `column` and `tab` must send their children inline in the create call. Other blocks with children can be created first, then have their children appended. `table_width` can't be changed after creation, so strip it from update payloads. An original `synced_block` must send `synced_from: null` explicitly.
- These round-trip through read → recreate: heading_1–4, paragraph, bulleted/numbered list items, to_do, toggle, quote, callout, code, equation, divider, table + table_row, table_of_contents, breadcrumb, bookmark, embed, external image, link_to_page, column_list, synced_block, tab, and date and page mentions.
- These can't be recreated: `child_page`/`child_database` (use `pages.create`), `link_preview`, `button`, `template` ("Cannot create a template block"), `meeting_notes` (renamed from `transcription`, "Cannot create a meeting_notes block"), plus `ai_block`, `custom_block` and `unsupported`. Notion-hosted files (`type: "file"`) return 1-hour signed URLs and need re-uploading through the File Upload API. User mentions must be trimmed to `{id}` before re-sending, because the API rejects the echoed `name`/`type`/`bot` fields.
- **Rate limits.** 180 requests/min per connection, about 3/s (600/min on Business/Enterprise), plus a per-workspace cap. A 429 returns `rate_limited` with `Retry-After` in seconds. Retry 529 `service_overload` the same way, but never retry `public_api_request_blocked`. notion-client 3.1.0 retries 429s and 5xx itself with backoff, but not read timeouts: it raises `RequestTimeoutError` straight away, so the adapter must retry reads itself. A full rogue → rewind → verify cycle on the 12-block page takes about 55 requests, and the whole spike run took 165 requests in 55–100 s with no 429s.
- **Size limits.** 100 blocks per children array, 1,000 block elements per payload, 500 KB per payload, 2,000 characters per `text.content`, 1,000 per equation, 2,000 per URL. One append request takes at most 2 levels of nesting.
- **Blocks of a trashed page** (Phase 3 adapter). `GET /blocks/{id}` still answers 200 while the page is trashed, but every block on it reads `in_trash: true` and goes back to `false` when the page is untrashed. A block hash that includes `in_trash` would flag every block as changed in a dry run of a rewind that starts with an untrash. The adapter hashes a block as `{type, body}`, and counts a trashed block as absent only while its page isn't trashed.
- **Retrying writes.** Appending children isn't idempotent, so on a read timeout or a 5xx the adapter doesn't resend it (it can't tell whether Notion ran it). A 429 or 529 means Notion refused the request, so resending any call is safe. Updates and deletes are safe to resend either way. The adapter calls the API through httpx directly, not notion-client.
